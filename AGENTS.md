# Prototype Instructions

## Approved scope

This is the user's isolated desktop and mobile canvas UX prototype. Keep all page edits in memory only; do not persist edited content or send it to services. Reload restores the default FORMA gallery. The private GitHub repository and Vercel deployment exist; the user has approved publishing the mobile iteration. Topbar, section edit/visibility/delete, link editing, and image editing are intentional demos; section dragging is functional; mobile menus open and Done finishes text editing.

The closest editable target owns the contextual toolbar; its section and repeatable-item ancestors keep their own toolbars visible while the pointer is anywhere inside them. Each level has a separate panel. Maintain this action order: image replacement/editing, item link, duplicate/delete, then a drag handle. Every adjacent action group uses the same 6 px gap without a divider line or extra margin before the handle (`--tool-group-gap`); preserve the left/right distribution of section actions. No arrow reorder buttons. Preserve the 36 × 36 px canvas-control geometry, including the drag handle, white topbar and separate white section-tool groups without a full-width background. Use Tabler Icons for canvas controls, not the original exported SVGs: PhotoEdit for image editing, PhotoUp for replacement, CopyPlus for duplication, ArrowsMove for dragging. Canvas toolbar icons are 18 px for both mouse and touch, with a 1.75 stroke. Use the is.art Gray presets from Figma node 11770:27581 through CSS variables: Gray/800 background, Gray/700 hover, Gray/900 pressed, Gray/50 foreground, Gray/600 borders, Gray/500 disabled. Keep canvas content colors separate from editor controls. Section controls are the light exception: white buttons, Gray/300 borders, Gray/100 hover, Gray/200 pressed, and the shared topbar icon color #505662. Keep the labeled Edit block button with a Tabler Pencil and optional background-image tools on the left; visibility/delete and the single section drag handle form separate groups on the right, with 6 px between groups. Section icons are 18 px inside 36 × 36 px buttons. Edit block has the same 36 px height and intrinsic width, the same label typography as Preview (14 px, weight 600, normal line height) through a shared CSS rule, 10 px side padding and an 8 px icon gap. The section wrapper is at least 48 px high including 6 px vertical padding; child controls stay 36 × 36 px. All section actions stay visible on touch and narrow screens, without a more menu. Wrap whole groups onto a second row when needed; measure its final width and wrapped height before positioning descendants. The empty section toolbar wrapper has no background and no pointer events; only visible, non-exiting buttons receive the pointer. Preserve fade/keyboard behavior and child toolbar collision placement.

Text editing, duplication, deletion with a last-item guard, and sorting within each original list are functional. Drag starts only from the handle after 6 px. Escape and dropping outside the original container cancel. Desktop Chrome at 1024, 1440, and 1920 px and touch at 320, 390, 430, and 768 px are the requested scope. Target mobile browsers are Android Chrome and iOS Safari; distinguish emulated checks from real-device keyboard and selection checks. A global undo history is excluded.

Repeatable items must apply sortable transforms through CSS.Translate.toString, never CSS.Transform.toString: rectSortingStrategy includes scaleX/scaleY that stretches unequal-width menu labels and mixed-size cards. Keep DragOverlay adjustScale={false}. Preserve translation transitions and grid/wrapped-menu sorting. Check intermediate-frame dimensions, final order and cancellation with runSortSizeChecks in tests/drag-scroll-checks.js.

During item dragging, only the moving preview has a selection outline. Do not outline the over/destination sibling: it looks like a second focused item. Do not add insertion lines for repeatable items; the dimmed source and smoothly displaced neighbours provide placement feedback. Keep native keyboard focus styles outside dragging. Run runDragFeedbackChecks in tests/drag-scroll-checks.js for both directions, mouse/touch, absence of extra outlines/lines, cleanup and focus preservation.

Keep the SortableContext ID array stable across hover/drag renders; recreating it makes dnd-kit disable sibling transitions and causes first-time displacements to jump. When a portal handle sits outside its item, preserve the grip offset and use a projected point inside the dragged item for collision and drop validation. A direct drop on an original-list label is also valid when the projection falls outside the container. The fixed topbar is never a valid drop target. Finish structural motion before measuring the grip. Preserve wrapped-menu sorting and the original-list boundary; never expand the entire canvas into a drop zone.

The first canvas section is a compact three-part menu: a local SVG logo image on the left, five repeatable links in the middle, and an editable Log in link-button on the right. The logo uses the ordinary image target `menu.logo` with replacement/edit tools; `menu.login` uses the ordinary link toolbar and no navigation. Both are separate from the repeatable menu list. The section padding is 8 px above and below, with no fixed height so long labels and wrapped rows still fit. Keep the base menu compact. The current experiment temporarily adds top padding when actual section buttons overlap a nested image or link by more than half the underlying image/link’s full height; follow the temporary-clearance rules below. Its portal already stacks above content. All section toolbars now use separate white groups, with no spanning backdrop. Empty space lets the user click and edit the menu underneath; the actual control buttons still take precedence where they overlap content. Each menu label is part of its repeatable item, so hovering the label shows the shared link/copy/delete/drag toolbar above the item. Clicking the label edits plain text; Enter finishes. Links wrap into multiple rows when needed and sort within the menu only. Link editing remains an icon-only demo, consistent with the rest of the prototype.

Button, text-link, and menu toolbars align exactly with the element's right edge, without a right inset. For these compact targets the toolbar sits above the element so it does not cover editable text; it flips below when the fixed editor bar leaves insufficient space above. When scrolled under the fixed editor bar, the section toolbar touches its bottom edge with no gap. Preserve the 8 px inset for ordinary item tools.

The fixed topbar keeps its original Site Builder design: Lucide ChevronLeft/ChevronDown/Settings/Palette/Eye, white background, original neutral borders and text, and the purple Save Changes button (#8054dd). Canvas icon/palette/size experiments do not apply to this topbar.

## Mobile and hybrid input

Separate responsive layout from input mode. At <=767 px shorten the section action label to Edit (keep its full accessible name) and make the circular boundary + buttons 36 × 36 px, centred on the boundary with top: -18px. These sizes follow viewport width, including mouse use on a phone-sized window. At <=767 px use the measured Site Builder header: 57 px plus safe-area inset, back, Main page, purple Save, and a more menu with Settings, Change theme, Preview. During touch editing show Done instead of Save. Phone content uses 20 px side padding and 48 px section spacing, one-column cards except the two-column duets list, image above about text, vertical events/footer. Canvas navigation stays visible and wraps below the logo/login row. Keep test fixtures 32 × 32, 180 × 72, and 4 px gaps. At 768–1199 px use two card columns; preserve the desktop layout above that.

The centralized touch controller accepts one-pointer taps on release only: <=10 px movement and <=300 ms duration. First tap selects the nearest target and ancestor tools without enabling contenteditable or opening the keyboard. A later tap on the same field enables plaintext editing and positions the caret at the touch point. Swipes, long contact, pointercancel and multi-touch do not select. Tapping another target finishes current editing and selects it without immediately editing. Repeat taps on a selected image or free background deselect. Done, Escape, Enter on single-line labels, and outside taps finish editing. Keep native text selection/paste/undo and active text >=16 px; do not overwrite focused DOM. Mouse input retains hover even on narrow or hybrid devices.

Touch tools use the same 36 × 36 px buttons as mouse input, with 18 px icons, the same colors and 5 px radius. Edit block remains wider to fit its label. Section background actions, visibility, delete and Drag block are shown directly in white groups. The editor topbar retains its own sizes and more menu; these canvas changes do not apply to it. Touch selection survives scroll. Hide the entire ancestor chain only when the selected target leaves the visible workspace, and restore it on return. No hover dwell or hover tooltips for touch; keep the short fade and reduced-motion support.

Use src/viewport.js for actual header bottom, VisualViewport offsets/size, and safe-area bounds. Feed the same bounds to toolbar placement, drag validation, caret reveal and edge autoscroll; do not hardcode 66 px in runtime callers. Tools may extend outside tiny targets. Compact item tools prefer 7 px above, then below. Descendants avoid actual ancestor button groups with a 6 px gap; near screen edges search below, above, then to the sides. Coordinates never animate. Touch drag uses the existing PointerSensor with touch-action:none set ahead of time only on handles. Phone one-column lists use verticalListSortingStrategy to avoid stretching unequal-height siblings; wrapped menus and the two-column duets list keep rectSortingStrategy for movement across columns and rows. Second finger/pointercancel cancel drag, and successful drops retain selection. Copy/delete clear selection and suppress the gesture's trailing click. See tests/mobile-checks.js and UX-PATTERNS.md for checks.

## Structural motion and tooltips

Canvas toolbar groups and standalone tool buttons use a 5 px outer corner radius (`--tool-radius`). Shared edges inside a group remain square. This applies to dark child controls and white section controls; the topbar and content buttons retain their own styles.

Pointer-triggered copy/delete uses `src/useCanvasMotion.js`: capture current visual positions before changing data, then animate transform/opacity with WAAPI. Reflow lasts 240 ms with the shared ease-in-out token; a new copy appears from the original’s direction with a 12 px offset and scale .97, after 40 ms for 200 ms with ease-out. Deletion updates data immediately and leaves an inert, aria-hidden visual for 160 ms. Strip all editor IDs and editable/focus attributes from this visual. Keep following sections continuous too. Rapid edits retarget from the current frame; finish outstanding motion before drag, resize or reduced-motion changes. Never animate typing or initial loading. Keyboard actions are immediate; reduced motion uses only 125 ms fades. Preserve last-item guards and suppression of accidental repeated actions. Run `tests/structural-motion-checks.js` for grids, mixed-width cards, rows, menus, interruption and cleanup.

Tooltips are a single portal layer in `src/Tooltip.jsx`, centered 8 px below each tool button. Clamp within the visible viewport with 8 px margins; flip above if needed at the bottom. Initial pointer delay is 450 ms, fade 125 ms. Moving to another tool within 300 ms of an open tooltip skips delay/fade; keyboard focus is immediate. Never show mouse and focus tooltips simultaneously. The tooltip follows its owner during layout motion and disappears when its owner becomes hidden or disconnected.

## Local workflow

Keep persistent ancestors stable: section → repeatable card/row → hovered image/link. Place each panel at its own anchor, measuring the entire hierarchy before paint. If a child would overlap an ancestor, place it below with a 6 px gap while preserving its horizontal anchor; do not move the parent. Image tools are centered on both axes of the full image. Item tools and link tools remain right-aligned. Preserve the image center unless its tools actually collide with an ancestor or viewport boundary. Keep compact link/menu tools off their text labels. Recalculate the stack on scroll/resize. At the viewport bottom, use free space to the left if there is no room below. Moving through any active panel or its safe gap retains the whole hierarchy. Test zero image padding in `tests/hierarchical-tools-checks.js`; the page keeps its existing 6 px spacing.

For a section toolbar, collision obstacles are the actual visible button groups, not its transparent full-width wrapper or padding. Measure those groups after positioning the section panel and before placing descendants. Card/image/link tools may share the section's row in the free space between groups; move them down by 6 px only when real controls conflict. Keep compact ancestor panels as one obstacle. Check both free-space placement and collisions with Edit block and the right action groups using `runSectionCollisionChecks` in `tests/edge-case-checks.js`.

## Section dragging

The white section toolbar ends with one 36 × 36 ArrowsMove grip labelled Drag block, replacing both arrow buttons. It reorders entire sections in memory using an outer DndContext and verticalListSortingStrategy; nested repeater contexts remain independent. Keep section IDs and React keys stable so edited content and nested list order survive movement. Preserve `narrow` in EditorContext: repeaters need it for their unequal-height phone strategy.

Start only from the grip after 6 px. Show an inert DOM snapshot without editor IDs, a dimmed source, smoothly displaced neighbours and a boundary insertion marker. Resolve pointer collisions at the grip rather than the centre of very tall sections. Escape, pointercancel, a second touch, or release outside the visible canvas cancel. Autoscroll uses the measured workspace bounds for both mouse and touch. A successful touch move retains the section selection; offscreen panels hide and return normally. Check `tests/section-drag-checks.js` and nested mobile drag regression.

Touch placement fallback rows must be ordered relative to the object's natural anchor: nearest below first, nearest above second, then sides. Never search all ancestor bottoms from the viewport top; that makes small-image tools jump under a distant pinned section strip instead of staying 6 px below their own card actions. At the bottom edge, prefer the nearby free row above the card tools. Preserve image horizontal centring and collision checks against every ancestor group.

## Temporary clearance experiment

At activation, section and item toolbars measure their real individual button rectangles against descendant image targets, content links and menu labels. A positive horizontal intersection and covered vertical length strictly greater than half the underlying image/link’s full height triggers temporary extra top padding. The denominator is the content height, never the button height: 36 px over a 72 px image is exactly 50% and does not trigger it; a fully covered 24 px logo does. Merge covered vertical intervals from actual buttons, counting adjacent buttons only once and excluding gaps between wrapped rows. Exactly 50%, normal text, transparent gaps between controls, and background images do not trigger it. Add only the maximum missing amount to put affected content 6 px below the overlapping controls; existing author padding is retained.

`src/toolbar-clearance.js` latches each owner's result, including zero, for its activation session. Switching descendants, editing, scrolling and drag do not recalculate or collapse its space. Apply before descendant toolbar measurements. Release departed owners when selection/hover leaves; restore original inline padding exactly. On edit blur wait 350 ms for a possible outside touch (max 300 ms) to complete; a new choice cancels the cleanup. On viewport resize remeasure the responsive base padding unless editing or dragging. A drag preview keeps the active item's temporary padding.

Do not try to push a large image whose top is already clipped under the editor header entirely below a pinned toolbar: that would insert potentially hundreds of pixels while scrolled. Such content keeps existing overlay placement. Do not accumulate padding as new content scrolls under the same toolbar. This is temporary editor UI, never content data or persistent storage. The first geometry change is synchronous before the toolbar's existing fade; no padding/position transition competes with hover hit-testing.

Run `tests/toolbar-clearance-checks.js` for both mouse and touch, plus the mobile and drag regressions. The tests cover content-relative 50% coverage of large and small images, including exactly 50%, section and card activation, text edit retention, restoration, and original inline padding.

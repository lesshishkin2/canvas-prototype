# Prototype Instructions

## Approved scope

This is the user's isolated desktop canvas UX prototype. Keep all page edits in memory only; do not persist edited content or send it to services. Reload restores the default FORMA gallery. The user has authorized a private GitHub repository and deployment to Vercel. Topbar, section actions, link editing, and image editing are intentional demos.

The closest editable target owns the contextual toolbar; its section and repeatable-item ancestors keep their own toolbars visible while the pointer is anywhere inside them. Each level has a separate panel. Maintain this action order: image replacement/editing, item link, duplicate/delete, then a drag handle separated by an 8 px gap without a divider line. No arrow reorder buttons. Preserve the 28 × 28 px child-control geometry, including the drag handle, white topbar and separate white section-tool groups without a full-width background. Use Tabler Icons for canvas controls, not the original exported SVGs: PhotoEdit for image editing, PhotoUp for replacement, CopyPlus for duplication, ArrowsMove for dragging. Compact icons are 16 px with a 1.75 stroke. Use the is.art Gray presets from Figma node 11770:27581 through CSS variables: Gray/800 background, Gray/700 hover, Gray/900 pressed, Gray/50 foreground, Gray/600 borders, Gray/500 disabled. Keep canvas content colors separate from editor controls. Section controls are the light exception: white buttons, Gray/300 borders, Gray/100 hover, Gray/200 pressed, and the shared topbar icon color #505662. Keep the labeled Edit block button with a Tabler Pencil and optional background-image tools on the left; visibility/delete and up/down form separate groups on the right, with 8 px between groups. Section icons are 16 px inside 34 × 34 px buttons, matching the measured Tilda controls. Edit block has the same 34 px height and intrinsic width, the same label typography as Preview (14 px, weight 600, normal line height) through a shared CSS rule, 10 px side padding and an 8 px icon gap. The section wrapper is 46 px high including 6 px vertical padding; child controls stay 28 × 28 px. The empty section toolbar wrapper has no background and no pointer events; only visible, non-exiting buttons receive the pointer. Preserve fade/keyboard behavior and child toolbar collision placement.

Text editing, duplication, deletion with a last-item guard, and sorting within each original list are functional. Drag starts only from the handle after 6 px. Escape and dropping outside the original container cancel. Desktop Chrome at 1024, 1440, and 1920 px is the requested scope; touch and a global undo history are excluded.

Keep the SortableContext ID array stable across hover/drag renders; recreating it makes dnd-kit disable sibling transitions and causes first-time displacements to jump. When a portal handle sits outside its item, preserve the grip offset and use a projected point inside the dragged item for collision and drop validation. A direct drop on an original-list label is also valid when the projection falls outside the container. The fixed topbar is never a valid drop target. Finish structural motion before measuring the grip. Preserve wrapped-menu sorting and the original-list boundary; never expand the entire canvas into a drop zone.

The first canvas section is a compact three-part menu: a local SVG logo image on the left, five repeatable links in the middle, and an editable login link-button on the right. The logo uses the ordinary image target `menu.logo` with replacement/edit tools; `menu.login` uses the ordinary link toolbar and no navigation. Both are separate from the repeatable menu list. The section padding is 8 px above and below, with no fixed height so long labels and wrapped rows still fit. The user intentionally wants the section toolbar to overlap the menu content: do not reserve clearance for it. Its portal already stacks above content. All section toolbars now use separate white groups, with no spanning backdrop. Empty space lets the user click and edit the menu underneath; the actual control buttons still take precedence where they overlap content. Each menu label is part of its repeatable item, so hovering the label shows the shared link/copy/delete/drag toolbar above the item. Clicking the label edits plain text; Enter finishes. Links wrap into multiple rows when needed and sort within the menu only. Link editing remains an icon-only demo, consistent with the rest of the prototype.

Button, text-link, and menu toolbars align exactly with the element's right edge, without a right inset. For these compact targets the toolbar sits above the element so it does not cover editable text; it flips below when the fixed editor bar leaves insufficient space above. When scrolled under the fixed editor bar, the section toolbar touches its bottom edge with no gap. Preserve the 8 px inset for ordinary item tools.

The fixed topbar keeps its original Site Builder design: Lucide ChevronLeft/ChevronDown/Settings/Palette/Eye, white background, original neutral borders and text, and the purple Save Changes button (#8054dd). Canvas icon/palette/size experiments do not apply to this topbar.

## Structural motion and tooltips

Canvas toolbar groups and standalone tool buttons use a 5 px outer corner radius (`--tool-radius`). Shared edges inside a group remain square. This applies to dark child controls and white section controls; the topbar and content buttons retain their own styles.

Pointer-triggered copy/delete uses `src/useCanvasMotion.js`: capture current visual positions before changing data, then animate transform/opacity with WAAPI. Reflow lasts 240 ms with the shared ease-in-out token; a new copy appears from the original’s direction with a 12 px offset and scale .97, after 40 ms for 200 ms with ease-out. Deletion updates data immediately and leaves an inert, aria-hidden visual for 160 ms. Strip all editor IDs and editable/focus attributes from this visual. Keep following sections continuous too. Rapid edits retarget from the current frame; finish outstanding motion before drag, resize or reduced-motion changes. Never animate typing or initial loading. Keyboard actions are immediate; reduced motion uses only 125 ms fades. Preserve last-item guards and suppression of accidental repeated actions. Run `tests/structural-motion-checks.js` for grids, mixed-width cards, rows, menus, interruption and cleanup.

Tooltips are a single portal layer in `src/Tooltip.jsx`, centered 8 px below each tool button. Clamp within the visible viewport with 8 px margins; flip above if needed at the bottom. Initial pointer delay is 450 ms, fade 125 ms. Moving to another tool within 300 ms of an open tooltip skips delay/fade; keyboard focus is immediate. Never show mouse and focus tooltips simultaneously. The tooltip follows its owner during layout motion and disappears when its owner becomes hidden or disconnected.

## Local workflow

Keep persistent ancestors stable: section → repeatable card/row → hovered image/link. Place each panel at its own anchor, measuring the entire hierarchy before paint. If a child would overlap an ancestor, place it below with a 6 px gap while preserving its horizontal anchor; do not move the parent. Image tools are centered on both axes of the full image. Item tools and link tools remain right-aligned. Preserve the image center unless its tools actually collide with an ancestor or viewport boundary. Keep compact link/menu tools off their text labels. Recalculate the stack on scroll/resize. At the viewport bottom, use free space to the left if there is no room below. Moving through any active panel or its safe gap retains the whole hierarchy. Test zero image padding in `tests/hierarchical-tools-checks.js`; the page keeps its existing 6 px spacing.

For a section toolbar, collision obstacles are the actual visible button groups, not its transparent full-width wrapper or padding. Measure those groups after positioning the section panel and before placing descendants. Card/image/link tools may share the section's row in the free space between groups; move them down by 6 px only when real controls conflict. Keep compact ancestor panels as one obstacle. Check both free-space placement and collisions with Edit block and the right action groups using `runSectionCollisionChecks` in `tests/edge-case-checks.js`.

The “Когда места мало” section after studies is an editable, sortable `edges` list: a wide image (centered tools with no collision), a 180 px card with a short 180 × 72 px image and zero padding (image tools collide and move below the parent by 6 px), and a link near the top-right of a card (link tools move below parent tools and below the label if needed). Keep these cases reproducible across desktop widths. `tests/edge-case-checks.js` checks their first frames, safe access, scrolling, copying, deletion, and mixed-width sorting.

The “Место для действия” edge-case card puts its link-button 16 px from the top and right edges. The user decided against placing content buttons directly in card corners; preserve these insets.

The same section also contains a separate sortable `edgeSamples` list with six additional scenarios: a 32 × 32 image, two inline images 4 px apart, four nearby links wrapping into two rows, empty paragraph/button fields, a short/tall card pair, and a 40 px compact row. Keep the original `edges` list's geometry and sorting isolated. All sample fields are flat strings so duplication remains independent; derive every nested target ID from the item ID, including `image2` and extra links. The compact row has a minimum height, not a fixed height, to accommodate edited text.

The “Рассмотреть ближе” section after the collection contains the independent `studies` list. Its repeatable cards have ordinary inline images, not backgrounds or item links. Card tools are exactly duplicate/delete/drag; the nested image owns only replacement/editing tools. Hovering the image, text or button preserves the parent toolbar; only the child panel changes. Keep image targets and text fields unique when duplicating, and omit editor targets from the drag preview.

The user is testing tight image spacing in these cards: keep only 6 px between the image and the top/side card edges. Text retains its 20 px side inset. Do not reserve a large empty strip above the image for parent tools.

Each studies card also contains a button with an editable label and its own link-edit demo toolbar. It is a nested link target; the parent card still has only duplicate/delete/drag.

Editable standalone images (`data-kind="image"`, including the logo and inline card images) receive a subtle white overlay at 16% opacity while their contextual tools are active. Drive it from the centralized `data-target-hover` state, not independent CSS hover, so it shares hover dwell and persists while moving onto tools. Use a non-interactive, absolutely positioned pseudo-element limited to the image bounds, with a 125 ms opacity transition and the shared ease-out. Keyboard focus, reduced motion, editing and dragging bypass this fade; editing/dragging hide it. Background cards and hero images keep their existing treatment.

An already open inset item/image toolbar owns a protective hover bridge across its 8 px top and right gaps. Retain it there even over a nested image, without a DOM overlay that intercepts clicks. Test actual slow pointer paths using hit-testing, not just isolated hover states.

Hover appearance and target changes require 150 ms on the same candidate; preserve the current target until then. Movement inside that candidate does not restart the timer. Returning to the active target, its protective bridge or its toolbar cancels the pending change. Keep the existing 180 ms close delay. Keyboard focus and text editing respond immediately. Cancel stale pending targets on editing, pointer actions, drag, structural actions, scroll, resize, window exit and blur. Keep the rationale and current values in UX-PATTERNS.md up to date with code changes.

Scroll and resize also recheck the content under the last pointer position once per animation frame, ignoring portal toolbars and movement-only protective bridges. Immediately remove departed owners while retaining shared ancestors; new targets use the 150 ms dwell after scrolling settles. Never leave card actions below the card's bottom edge when it is clipped under the topbar. Keyboard focus invalidates the stored pointer until it moves again; window exit/blur also invalidates it. Editing, dragging and suppression after structural actions must not be bypassed by scroll. Exercise real scrolling without pointermove in `tests/scroll-hover-checks.js`.

Toolbar geometry must not wait for a React commit or an extra animation frame. Write geometry synchronously on layout/scroll/resize; regular portal panels use absolute document coordinates so browser scrolling moves them with their content. Only a section panel pinned below the topbar uses fixed positioning. React owns availability/fades, not per-frame coordinates. Keep boundary “+” buttons fully above neighbouring canvas content: the active section's stacking context sits above its neighbours, while editor panels and the topbar keep their higher layers. Exercise external/wrapped menu grips, intermediate sorting frames, same-turn scroll alignment and boundary hit-testing in `tests/drag-scroll-checks.js`.

Each toolbar owner has fresh intrinsic measurements before its first visible frame; never reuse a section's positioned width for a compact toolbar. Observe the panel as well as its anchor. Hover entry/exit uses opacity only, 125 ms with cubic-bezier(0.23, 1, 0.32, 1); never animate toolbar coordinates or dimensions. A closing panel is inert, aria-hidden, non-interactive and excluded from hover resolution. Return during its exit reverses the same transition immediately. Replace owners at the same level without overlapping icon sets. Keyboard focus, editing, drag, structural actions and reduced motion bypass fades. Check first-visible-frame geometry in tests/toolbar-motion-checks.js.

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.
